# Recipe Dost 1.0.1 Beta Release Runbook

Date: 2026-07-16

## Release identity

- Play release name: `Recipe Dost 1.0.1 Beta (2)`
- Expo/Android `versionName`: `1.0.1`
- Android `versionCode`: `2`
- Android package: `com.recipedost.app`
- EAS build profile/environment: `production` / `production`
- Artifact: Android App Bundle (`.aab`)
- Play track: Internal Testing
- Version source: local; production auto-increment is intentionally absent
- EAS project ID and existing Android signing/upload-key ownership are unchanged

## Release architecture audit

The app uses Expo continuous native generation; no `android/` directory is
committed. `app.config.js` is the native version/package source, and Settings
reads Expo/native application metadata rather than hardcoded screen copy. There
is no runtime-version policy, EAS Update channel, or release branch configured,
and this release must not publish an EAS Update.

The production build profile selects the production EAS environment, production
app variant, store package, and AAB output. Both controlled Sentry/PostHog test
flags are pinned false. Production runtime configuration fails closed when
required values are absent or invalid. The Sentry Expo plugin is production-only,
and Metro supplies debug IDs for production source-map matching. The submit
profile targets Internal Testing as a draft so a human reviews the release in
Play Console before rollout.

Expo Doctor also identified a missing `expo-font` native peer required by the
existing vector-icon system. The release adds that peer/config plugin and aligns
only compatible SDK 56 patch releases; it does not upgrade the Expo SDK.

## Phase 1: validate and promote `develop`

1. Keep the release-preparation commit on `develop`; do not build production
   from `develop` and do not use `ALLOW_NON_MAIN_PROD_BUILD`.
2. Confirm the branch is clean and current:

   ```sh
   git switch develop
   git pull --ff-only origin develop
   git status --short --branch
   ```

3. Run the automated release gate:

   ```sh
   npm run qa:static
   npm run test:release
   npm run test:observability
   npm run test:onboarding
   node scripts/env/env-doctor.mjs development
   node scripts/env/validate-env.mjs development
   node scripts/env/validate-env.mjs production
   npm run functions:check
   ```

4. Run Android development-device QA using the matrix below. Fix blockers on
   `develop`, rerun the relevant check, then repeat the final gate once.
5. Push `develop` and open a `develop` -> `main` pull request. Review the diff,
   confirm only the expected migration is pending, and merge only after QA signoff.
   At preparation time `main` is zero commits ahead and `develop` is 16 commits
   ahead, so a fast-forward is possible if branch protection permits it.
6. After merge, update local `main` without creating a second merge commit:

   ```sh
   git switch main
   git pull --ff-only origin main
   git status --short --branch
   ```

## Phase 2: deploy the required production database migration

The `main...develop` release diff adds only
`20260711080652_m22e_recipe_management.sql`. Production currently does not have
it. It adds favorite/soft-delete columns and the active-library index used by
the new app. Deploy it before distributing build 2.

1. Validate the production environment without exposing values:

   ```sh
   node scripts/env/validate-env.mjs production
   ```

2. Link the CLI to the production project through the guarded env loader:

   ```sh
   node scripts/env/run-with-env.mjs production -- sh -c 'supabase link --project-ref "$SUPABASE_PROJECT_REF" --yes'
   supabase migration list --linked
   ```

3. Preview the production change. Stop if anything other than the expected
   migration is pending:

   ```sh
   supabase db push --linked --dry-run
   ```

4. After human approval, apply and verify:

   ```sh
   supabase db push --linked
   supabase migration list --linked
   ```

5. Relink local CLI state to development immediately:

   ```sh
   node scripts/env/run-with-env.mjs development -- sh -c 'supabase link --project-ref "$SUPABASE_PROJECT_REF" --yes'
   supabase migration list --linked
   ```

No Supabase Edge Function changed between `main` and `develop`, so do not
redeploy functions for this release. No Python worker code/config changed in
this repository diff, so do not redeploy Render. Existing production services
receive smoke verification only.

## Phase 3: production preflight and AAB generation

1. From clean, merged `main`, run the non-building preflight:

   ```sh
   npm run build:prod:dry
   ```

2. The preparation audit found that production EAS does not yet contain
   `EXPO_PUBLIC_SENTRY_DSN`, `EXPO_PUBLIC_POSTHOG_API_KEY`,
   `EXPO_PUBLIC_POSTHOG_HOST`, `SENTRY_ORG`, `SENTRY_PROJECT`, or
   `SENTRY_AUTH_TOKEN`. After checking the dry-run key list, sync the allowlisted
   production app values and Supabase secrets through the established workflow:

   ```sh
   npm run env:deploy:prod
   ```

   The helper intentionally does not sync `SENTRY_AUTH_TOKEN`. Create or replace
   that value interactively as a project-scoped EAS secret; never put it on a
   command line or commit it:

   ```sh
   eas env:create production --name SENTRY_AUTH_TOKEN --visibility secret
   ```

   Confirm names/visibility without displaying sensitive values:

   ```sh
   eas env:list production --format long
   ```

3. In the EAS dashboard, confirm the production environment contains all
   required variables, `SENTRY_AUTH_TOKEN` is secret, and both controlled test
   flags are false. Confirm the existing Android build credential/upload key is
   selected; do not generate or replace it.
4. Create the build only after the database migration and external checks pass:

   ```sh
   npm run build:prod
   ```

   This established wrapper rechecks `main`, validates production env, rejects
   the known development Supabase project and RevenueCat Test Store keys, runs
   static QA, syncs allowlisted production EAS/Supabase configuration, and runs
   `eas build --platform android --profile production`.
5. In the EAS build page/logs, verify:

   - package `com.recipedost.app`, version `1.0.1`, version code `2`
   - production profile/environment and `.aab` artifact
   - existing Android signing credential was used
   - Sentry source-map upload ran successfully; any missing token/org/project or
     upload failure is a release blocker
   - no EAS Update was published

## Phase 4: upload to Google Play Internal Testing

### Recommended manual path

1. Download the `.aab` from the successful EAS build page.
2. Open Play Console -> Recipe Dost -> Testing -> Internal testing.
3. Open the Releases tab and choose Create new release.
4. Keep Google Play App Signing/upload-key settings unchanged and upload the AAB.
5. Confirm Play reads version name `1.0.1` and version code `2`. Stop on a
   duplicate code, package mismatch, signing mismatch, or unexpected permission.
6. Set release name to `Recipe Dost 1.0.1 Beta (2)`.
7. Add the release notes below, save, review warnings, then select Review release.
8. Start rollout to Internal Testing only. Do not promote to closed, open, or
   production during M22E.3A.
9. On the Testers tab, keep the approved tester list, feedback contact, and
   opt-in link. Add billing testers to Play license testing as required.

### Optional EAS Submit path

The first Play upload has already occurred, but EAS submission still requires a
Google service account with Play permissions stored in EAS credentials. No key
file or service-account credential is committed in this repository. After an
owner confirms that EAS credential, submit the successful build as a draft:

```sh
eas submit --platform android --profile production --id <EAS_BUILD_ID>
```

Then open Internal testing in Play Console, review the draft, add the release
name/notes if needed, and explicitly start the rollout. Do not use `--auto-submit`
for this release.

## Android acceptance matrix

### Install and upgrade

- Fresh install from Internal Testing: splash/bootstrap -> five-page Welcome ->
  Skip/Get Started -> Home; relaunch bypasses Welcome after completion.
- Upgrade over Play build 1 without clearing data: session, saved links, recipe
  cards, favorites, grocery lists, onboarding state, and Premium access remain.
- Confirm Settings reports `1.0.1 (2)` from Expo/native metadata.

### Core product flow

- Paste one supported recipe link and save it with and without an optional note.
- Share a supported link into Recipe Dost; save/share must not create a media job.
- Verify metadata loading/error/retry and duplicate-link handling.
- Explicitly generate an AI recipe; verify queued/processing/completed and one
  controlled failure/retry path without exposing raw video/CDN URLs.
- Verify Home/Library search, Recent/Favorites/AI Recipes, favorite persistence,
  soft delete, recipe detail, bilingual content, Grocery create/copy/share, and
  empty/loading/error/retry states.

### Auth, privacy, analytics, and errors

- Exercise anonymous bootstrap, returning session, sign-out/reset, offline
  launch, foreground/background, and killed-app reopen.
- Confirm production has no Developer section, debug banner, test-event button,
  localhost/preview endpoint, or sensitive console output.
- Verify one production PostHog funnel in Live Events with normalized screens,
  no content/URL/search/purchase identifiers, and no duplicate transitions.
- Trigger one approved unexpected technical error and verify Sentry environment,
  release/build, UUID-only identity, privacy sanitizer, and symbolicated frames.
- Confirm Session Replay, PostHog Error Tracking/exception capture, autocapture,
  tracing, and profiling remain disabled.

### RevenueCat and Play Billing

- Test real Internal Testing monthly/yearly packages and localized prices.
- Verify purchase cancellation is friendly and creates no Sentry exception.
- Verify purchase success appears only after RevenueCat entitlement and backend
  Premium access synchronize; no purchase payload reaches observability.
- Verify restore, already-owned/pending states, manage subscription, app restart,
  and cross-session Premium persistence.

### Production services

- Confirm favorite and soft delete work against production after the migration.
- Run approved production smoke links for supported providers and confirm the
  existing Edge Functions and worker remain healthy without redeployment.
- Review Play pre-launch report, crashes/ANRs, device compatibility, and policy
  warnings before widening the tester group.

## Rollback and completion

If a release blocker appears, stop or deactivate the Internal Testing release;
do not decrement or reuse version code 2. Fix forward on `develop` and ship the
next unused version code (at least 3). M22E.3A completes only when fresh-install
and build-1 upgrade QA pass, Sentry source maps and PostHog production delivery
are verified, purchases/restores pass, and no P0/P1 issue remains. Broader beta
QA and promotion decisions remain M22E.4.
